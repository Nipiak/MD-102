Ex 46
Entra ID Connect — PHS, PTA et Fédération ADFS
Débutant ⏱ 35 min 🏷 Identité hybride
▼
🎯 Objectif : Comprendre les trois modes d'authentification hybride proposés par Entra ID Connect (Password Hash Sync, Pass-Through Authentication, Fédération ADFS), choisir le mode adapté à chaque contrainte métier, puis vérifier l'état de la synchronisation via PowerShell et le portail Entra ID.
⚠️ Prérequis : Active Directory Domain Services on-prem, serveur Windows Server 2019+ avec accès Internet, compte Global Admin M365, Entra ID Connect installé (version ≥ 2.x).
📋 Schéma des 3 modes : 
┌──────────────────────────────────────────────────────────────────────────┐
│  MODE 1 — Password Hash Sync (PHS)        ← RECOMMANDÉ PAR MICROSOFT    │
│                                                                          │
│  AD on-prem ──► Entra ID Connect ──► Hash(Hash(mdp)) ──► Entra ID       │
│                 (agent sync)             (bcrypt)        (cloud auth)    │
│                                                                          │
│  ✅ Fonctionne même si on-prem offline    ✅ Entra ID Protection complet  │
│  ✅ Smart Lockout cloud                   ⚠️  Hash stocké dans le cloud   │
├──────────────────────────────────────────────────────────────────────────┤
│  MODE 2 — Pass-Through Authentication (PTA)                              │
│                                                                          │
│  Utilisateur ──► Entra ID ──► Agent PTA on-prem ──► DC Active Directory  │
│                  (cloud)      (validation)            (réponse Oui/Non)  │
│                                                                          │
│  ✅ Aucun hash dans le cloud              ❌ AD offline = connexion KO    │
│  ✅ Politique de MDP AD appliquée         ⚠️  Agent PTA = SPOF si 1 seul  │
├──────────────────────────────────────────────────────────────────────────┤
│  MODE 3 — Fédération ADFS                                                │
│                                                                          │
│  Utilisateur ──► ADFS (on-prem) ──► Claims/Token ──► Entra ID (trust)   │
│                  (STS)                                                   │
│                                                                          │
│  ✅ Scénarios d'auth complexes (smart card, certificat, MFA on-prem)     │
│  ❌ Infra complexe (ADFS farm + WAP)      ❌ ADFS offline = KO total      │
└──────────────────────────────────────────────────────────────────────────┘

Étapes — Audit et gestion d'un Entra ID Connect existant

  1. Vérifier l'état du service sur le serveur Connect : 
    Import-Module ADSync

# État du planificateur
Get-ADSyncScheduler | Select-Object SyncCycleEnabled, NextSyncCycleStartTime,
    CurrentlyRunning, LastSyncRunTime, SyncCycleInProgress

# État de chaque connecteur (AD et Entra ID)
Get-ADSyncConnector | Select-Object Name, Type, ConnectivityParameters
  2. Forcer une synchronisation delta : 
    # Sync delta (~2 min) — traite seulement les changements depuis la dernière sync
Start-ADSyncSyncCycle -PolicyType Delta

# Sync complète — réimporte tous les objets (utiliser avec précaution en prod)
# Start-ADSyncSyncCycle -PolicyType Initial
  3. Vérifier qu'un utilisateur AD est bien synchronisé :
    entra.microsoft.com → Identités → Utilisateurs → [utilisateur] → Propriétés → Source doit afficher Windows Server AD (et non Azure Active Directory qui = cloud-only).
  4. Identifier le mode d'authentification actif via Graph PowerShell : 
    Connect-MgGraph -Scopes "Domain.Read.All"
Get-MgDomain | Select-Object Id, AuthenticationType, IsDefault
# AuthenticationType :
#   "Managed"   = PHS ou PTA
#   "Federated" = ADFS ou fédération tierce
  5. Changer le mode PTA → PHS (si besoin de résilience) :
    Sur le serveur Connect → Entra ID Connect (assistant) → Modifier la connexion utilisateur → Password Hash Synchronization → terminez l'assistant. La transition est transparente pour les utilisateurs (aucune interruption).

Scénario : La DSI exige que les mots de passe ne soient jamais stockés, même sous forme de hash, dans le cloud Azure. L'AD on-prem doit rester la seule source d'authentification. Quel mode Entra ID Connect choisissez-vous ?
A. Password Hash Sync (PHS) — recommandé par Microsoft
B. Pass-Through Authentication (PTA) — validation on-prem, aucun hash dans le cloud
C. Fédération ADFS — le token SAML remplace le MDP
D. Cloud-Only — suppression de l'AD on-prem
✅ B — Pass-Through Authentication valide les credentials directement contre l'AD via un agent léger. Aucun hash n'est stocké dans Entra ID. Contrainte critique : si les DCs on-prem sont inaccessibles, toutes les connexions échouent. Déployez toujours au moins 2 agents PTA pour la résilience.

Rôles Entra ID & Unités Administratives — Délégation granulaire
Débutant ⏱ 30 min 🏷 RBAC Entra / Délégation
▼
🎯 Objectif : Configurer la délégation administrative dans Entra ID via des rôles intégrés et des Unités Administratives (AU) — permettre à un helpdesk régional de gérer uniquement les utilisateurs de sa région, sans accès au reste du tenant.
⚠️ Prérequis : Licence Entra ID P1 (incluse M365 E3/E5), rôle Global Admin, 2 utilisateurs de test (testuser01, testuser02) créés.
📋 Schéma — Unités Administratives : 
Tenant Contoso (scope global — Global Admin voit TOUT)
│
├── AU_France
│   ├── user_paris_01       ◄─ helpdesk_fr peut gérer ces utilisateurs
│   ├── user_lyon_01        ◄─ (rôle "User Administrator" scoped à AU_France)
│   └── user_bordeaux_01
│
└── AU_Allemagne
    ├── user_berlin_01      ◄─ helpdesk_de peut gérer ces utilisateurs
    └── user_munich_01      ✗  helpdesk_fr NE PEUT PAS y accéder

Sans AU : User Administrator = accès à TOUS les utilisateurs du tenant
Avec AU : User Administrator = accès UNIQUEMENT aux membres de l'AU assignée

Étapes

  1. Inventaire des rôles MD-102 clés :
    entra.microsoft.com → Identités → Rôles et administrateurs → parcourez et notez les permissions de : Intune Administrator, User Administrator, Cloud Device Administrator, Authentication Administrator.
  2. Créer une Unité Administrative :
    entra.microsoft.com → Identités → Unités administratives → + Créer
    Nom : AU_France → onglet Attribuer des rôles : laissez vide pour l'instant → Créer.
  3. Ajouter des membres à l'AU :
    AU_France → Utilisateurs → + Ajouter des membres → sélectionnez testuser01 et testuser02 → Sélectionner.
  4. Assigner un rôle scopé à l'AU :
    AU_France → Rôles et administrateurs → + Ajouter des attributions
    Rôle : User Administrator → Membre : helpdesk_fr@votredomaine.com → Ajouter.
  5. Tester la délégation :
    Connectez-vous avec le compte helpdesk_fr → naviguez vers entra.microsoft.com → Utilisateurs → tentez de réinitialiser le MDP de testuser01 (AU_France) → devrait fonctionner ✅
    Tentez sur testuser03 (hors AU_France) → devrait être refusé ✗.
  6. Vérifier les rôles d'un utilisateur via Graph : 
    Connect-MgGraph -Scopes "RoleManagement.Read.Directory"
$userId = (Get-MgUser -UserId "helpdesk_fr@contoso.com").Id

# Rôles directs (tenant-wide)
Get-MgUserTransitiveMemberOf -UserId $userId |
  Where-Object { $_.AdditionalProperties["@odata.type"] -eq "#microsoft.graph.directoryRole" } |
  Select-Object @{N="Rôle";E={$_.AdditionalProperties["displayName"]}}

# Rôles scopés à une AU
Get-MgRoleManagementDirectoryRoleAssignment -Filter "principalId eq '$userId'" |
  Select-Object RoleDefinitionId, DirectoryScopeId

Ex 48
Restrictions d'enrôlement Intune — Contrôler qui et quoi peut s'enrôler
Débutant ⏱ 25 min 🏷 Enrôlement / Sécurité
▼
🎯 Objectif : Configurer deux types de restrictions d'enrôlement Intune — type d'appareil (quelle plateforme, quelle version OS, BYOD autorisé ou non) et limite d'appareils (nombre max par utilisateur) — puis diagnostiquer les échecs depuis le portail et l'Event Viewer Windows.
⚠️ Prérequis : Rôle Intune Administrator, au moins un utilisateur de test avec licence Intune.
📋 Les deux types de restrictions et leur logique de priorité : 
RESTRICTION DE TYPE D'APPAREIL          RESTRICTION DE LIMITE D'APPAREILS
────────────────────────────            ─────────────────────────────────
Filtre : plateforme, version OS,        Filtre : nombre max d'appareils
         BYOD autorisé/bloqué                    enrôlés par utilisateur

Priorité : la restriction avec le numéro le PLUS BAS gagne (1 = plus haute priorité)
Défaut : Tous les utilisateurs → priorité la plus basse (s'applique en dernier recours)

Exemple :
  Priorité 1 : GRP_IT        → Windows 11 Pro+, BYOD autorisé, max 10 appareils
  Priorité 2 : GRP_Helpdesk  → Windows 11 seulement, BYOD bloqué, max 5 appareils
  Priorité 3 : Tous          → Toutes plateformes, BYOD bloqué, max 3 appareils

Étapes

  1. Créer une restriction de type — Bloquer les BYOD Windows :
    intune.microsoft.com → Appareils → Inscription → Restrictions d'inscription → Restrictions de type d'appareil → + Créer → Windows 10 et versions ultérieures
    Nom : RESTRICT_NoBYOD_Windows
      • Appareils personnels Windows : Bloquer
      • Version minimale de l'OS : 10.0.19045 (Win 10 22H2)
      • iOS/iPadOS : Autorisé | Android : Autorisé | macOS : Bloqué
    Assignez à GRP_Intune_Pilot | Priorité : 1.
  2. Créer une restriction de limite :
    Restrictions d'inscription → Restrictions de limite d'appareils → + Créer
    Nom : LIMIT_Helpdesk_5 | Limite : 5
    Assignez au groupe Helpdesk | Priorité : 1.
  3. Tester l'enrôlement bloqué :
    Sur une VM Windows 10 21H1 (inférieure au minimum configuré) → Paramètres → Comptes → Accès Professionnel → Se connecter → Enrôlement MDM → le message d'erreur doit indiquer version OS insuffisante.
  4. Lire les logs d'enrôlement sur le poste : 
    # Event Viewer via PowerShell — chercher les erreurs d'enrôlement
Get-WinEvent -LogName "Microsoft-Windows-DeviceManagement-Enterprise-Diagnostics-Provider/Enrollment" |
  Where-Object { $_.Level -in @(2,3) } |
  Select-Object TimeCreated, Id, Message |
  Sort-Object TimeCreated -Descending |

📍 Règles de précédence des politiques Intune

Contrairement aux GPO Active Directory (qui ont un ordre de précédence bien défini — LSDOU), Intune n'applique pas de précédence entre les profils de configuration. Si deux profils configurent le même paramètre avec des valeurs différentes, le résultat est un Conflit et aucune valeur n'est appliquée.
Type de politiqueComportement en cas de conflit
Profils de configuration❌ Conflit — aucune valeur appliquée
Politiques de conformité❌ Conflit — appareil marqué non conforme
Security Baselines vs Profils config❌ Conflit — aucune valeur appliquée
Paramètres de l'espace de travail (Settings Catalog) vs OMA-URI custom❌ Conflit si même CSP
Politiques de protection des applications (MAM)✅ La valeur la plus restrictive s'applique entre politiques MAM

🎯 Objectif : Intégrer Microsoft Defender for Endpoint (MDE) avec Intune pour centraliser l'onboarding des appareils, déployer la configuration EDR, et utiliser le signal de risque MDE dans les politiques de conformité Intune.
📋 Contexte : MDE est la solution EDR (Endpoint Detection & Response) de Microsoft. Son intégration avec Intune est bi-directionnelle : Intune orchestre l'onboarding MDE sur les appareils ; MDE remonte son niveau de risque à Intune qui peut conditionner la conformité sur ce signal.

Étapes d'intégration MDE ↔ Intune

  1. Activer la connexion Intune-MDE :
    Dans Intune → Sécurité des points de terminaison → Microsoft Defender pour point de terminaison → Activer la connexion → Ouvrir le portail Microsoft Defender.
  2. Dans le portail MDE (security.microsoft.com) :
    Paramètres → Endpoints → Fonctionnalités avancées → Activez Connexion Microsoft Intune.
  3. Créer un profil Endpoint Detection and Response (EDR) :
    Dans Intune → Sécurité des points de terminaison → Détection de point de terminaison et réponse → Créer une stratégie :
      • Plateforme : Windows 10 et versions ultérieures
      • Modèle : Détection de point de terminaison et réponse
      • Type de package de configuration client : Automatique depuis le connecteur
    Assignez à DYN_Windows11_Devices.
  4. Configurer la conformité basée sur le risque MDE :
    Dans Intune → Conformité → Stratégies de conformité → votre politique Windows → Microsoft Defender pour point de terminaison :
      • Exiger que l'appareil soit au niveau ou en dessous du score de risque de l'ordinateur : Faible
  5. Vérifier l'onboarding sur un appareil :
    Get-MpComputerStatus | Select-Object AMProductVersion, IsTamperProtected, RealTimeProtectionEnabled
    Dans le portail MDE : vérifiez que l'appareil apparaît dans Appareils → Inventory avec statut "Actif".
